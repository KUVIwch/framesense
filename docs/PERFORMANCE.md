# 性能测量与取舍

测量时间：2026-10-15（Asia/Shanghai）。环境：Windows 11 10.0.26200，64 位 Python 3.14.5，Intel64 Family 6 Model 154 Stepping 3。使用项目 `.venv` 与当前安装依赖。未联网，也未使用用户照片。

## 方法

`tools/benchmark.py` 生成三张确定性的渐变 JPG（质量 92），分别为 640×480、4912×3264 与 6000×4000。每张在独立子进程中测量：导入模块、加载、全局统计、图像自比较、左上四分之一面积区域分析，再重复加载和统计一次。计时使用 `perf_counter`；Windows `GetProcessMemoryInfo.PeakWorkingSetSize` 记录整个进程的工作集峰值，覆盖本地库分配。不是仅用 Python 分配跟踪器估计。

优化前在任何核心改动前测量，使用基线 `9e0ddde` 的算法；优化后使用同一批 JPG，通过 `AnalysisService` 执行相同工作顺序。基线全图/区域按原版实际方法计算，优化版使用有限分辨率近似。这是实际工作流成本比较，不是两种算法逐像素精度相同的声明。重复运行会受 OS 文件缓存、CPU 状态和首次导入影响；以下是各一次实际运行，没有虚构平均值或置信区间。

复现：

```powershell
.venv\Scripts\python.exe tools/benchmark.py --mode baseline --output work/performance/baseline-rerun.json
.venv\Scripts\python.exe tools/benchmark.py --mode optimized --output work/performance/optimized-rerun.json
```

`baseline` 模式从 Git 基线只读导出核心模块到忽略的工作目录，独立子进程使用历史模块；不切换当前分支，也不覆盖当前源码。素材与原始 JSON 保存在 `work/performance/`，该目录不提交。这里保留完整的主要测量数据。

## 具体改动

- 原图尺寸与预览数组分离，EXIF 转向后保留原始宽高；默认分析/显示预览最长边 1600。直接调用 `load_image()` 仍默认返回全尺寸，保留 CLI 兼容性；桌面使用有界服务。
- JPEG 尝试 `draft` 缩小解码；大 RAW 使用半尺寸 demosaic 后缩小，rawpy 仅实际导入 RAW 时加载。PNG 解压本身仍可能使用较高峰值。
- 统计最长边 1024、Lab 与区域最长边 512，比较最长边 256。直方图数量属于采样位图，不是原始像素数量。区域显示原图坐标，由服务映射到分析图；很小区域精度有限。
- 缓存默认保留最多 128 MiB、24 条，超限按最近使用时间淘汰；过大的条目不入缓存。缓存键包含内容 SHA-256、算法版本、处理参数和区域。每次加载重新散列内容，能识别同名同时间戳文件被替换。
- 图像数组只读，统计返回防御性副本；跨线程计算共享一个服务。缓存没有落盘。清空缓存可以释放其持有的引用；UI 或调用方仍持有的数组不在缓存上限内。

## 测量精度与剩余瓶颈

本轮修正了亮度权重与 HSL 饱和度定义，因此旧版与新版的统计值不应逐字相等。样本 6000×4000 的平均亮度由原 RGB 均值 126.95 变为 Rec.709 Y′ 126.46；其中既有定义差异，也有缩图影响。没有把这种变化伪装成浮点误差。

当前基准针对核心计算，不包括窗口冷启动、屏幕合成、鼠标拖动延迟或 GUI FPS；不能据此宣称缩放达到某一帧率。窗口响应、取消和快速切换由 GUI 回归另行验证。有限分辨率统计会丢失细小纹理和极小高光点；后续可增加按需高精度区域读取，不能直接把采样直方图用于原图溢出像素计数。

未获得真实 ARW 文件，因此第三类选择高分辨率 JPG，而不编造 RAW 耗时。PNG、带复杂 ICC 的广色域大图、不同相机 RAW 仍需真实样本测量。核心首次导入 colour-science 仍占主要固定时间；后续可在后台预热，或评估更轻的专用色彩实现，前提是验证计算一致性。

## Qt 事件循环实测补充

2026-10-15 09:48（Asia/Shanghai）使用 `tools/benchmark_gui.py` 测量真实 QApplication、MainWindow、显示事件以及照片导入到指导就绪的路径。Qt 平台设为 `offscreen`，仍构造实际控件并处理窗口事件，不创建虚假的 GUI 速度估计。原始结果保存在忽略目录 `work/gui-performance.json`。

复现命令：

```powershell
.venv\Scripts\python.exe tools/benchmark_gui.py --output work/gui-performance-rerun.json
```

脚本从 `baseline-colorlab-20261014` 通过 `git ls-tree` / `git show` 只读导出 `framesense/` 下的全部 Python 文件到 `work/gui-baseline/`；不读取 `.env`，不切换分支，工作目录始终为当前项目。基线与新版在两个独立子进程中依次执行，避免两套大图处理同时竞争内存。新版使用 `work/` 下独立临时数据库与草稿路径，结束时清理；基线不调用保存会话。

两张测试 JPG 尺寸均为 4912×3264，内容不同。参考图复用核心基准渐变素材，原片对 RGB 作确定性的轻微偏移后重存。素材没有用户照片。基线使用主线程 `load_image` 两次并更新两张视图，随后 `_update_stats()` 和 `_analyze()`；新版调用 `load_path('ref', ...)` 与 `load_path('src', ...)`，等待后台任务交付 `_guidance` 且当前任务全部完成。跳过文件选择对话框，未模拟人的操作间隔。第二轮重复导入相同两张图片并分析，测量热缓存路径。

窗口首次就绪在这个样本中略慢约 60ms，本轮没有证明窗口启动变快。首次双图工作流约从 11.3 秒缩短为 2.2 秒；同时 10ms PreciseTimer 持续收到事件，新版首次共记录 213 次回调，最大间隔约 49ms。基线计算时的最长间隔超过 11 秒，说明同步处理阻塞事件交付；新版的耗时主要转到后台，仍存在短时调度、控件刷新或持有 GIL 引起的间隔。计时器间隔是主线程事件处理响应的代理，不等同于鼠标输入延迟或画面刷新率。

以上每个版本仅一个进程、一次首次工作流与一次重复工作流，不提供统计置信区间。新进程不等于磁盘、字体或 OS 缓存被物理清空；这个测试不能宣称“硬件冷启动”。offscreen 也不覆盖 Windows 原生窗口合成、GPU、原生输入、真实屏幕缩放比例、DPI 或 FPS。它补充了自动 GUI 测试中的主线程响应证据，不能替代真实显示器上的目测与操作检查。
